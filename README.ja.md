# Verdict

### 🔗 インタラクティブなドキュメントの公開URL：[verdict.noahkawaguchi.com](https://verdict.noahkawaguchi.com)

---

Verdictは、[優先順位付投票制](https://ja.wikipedia.org/wiki/優先順位付投票制)を扱う、Swagger UIによるインタラクティブなドキュメント付きのサーバーレスREST APIです。投票の作成・票の送信・結果の取得が可能です。

一つだけの選択肢を選ぶのではなく、投票者はすべての選択肢を好みの順に順位付けします。即時決選投票アルゴリズムにより、過半数を得る選択肢が現れるまで、最下位の選択肢を繰り返し除外して票を再配分します。除外の際に同票となる場合は、再帰的な決選投票によって決定します。

## アーキテクチャ

このプロジェクトは完全にサーバーレスで構成されていて、API GatewayがリクエストをGoのLambda関数に転送し、その関数がDynamoDBの読み書きを行います。常時稼働するサーバーが不要なため、負荷がない時のコストはゼロになります。

主な設計上の判断：

- **Go**：Goは小さな自己完結型バイナリにコンパイルされ、メモリ使用量が少なく、コールドスタートが速いため、Lambdaとの相性が良好です。
- **単一のLambda関数**：内部ルーターを持つ一つの関数ですべてのルートを処理することで、小さなAPIにおける複数関数のデプロイ管理のオーバーヘッドを避けます。
- **DynamoDB**：シンプルなキーバリューのアクセスパターン（IDによる投票の取得、投票に対するすべての票の取得）がDynamoDBに適していて、リレーショナルなスキーマを必要としません。

## プロジェクト構成

コードベースの設計は、API・ドメイン・インフラの一般的な3層パターンに概ね従っていますが、プロジェクトの規模が比較的小さいため、実用的な観点から一部簡略化しています。

```
verdict/
├── cmd/              # Lambdaエントリーポイントと設定初期化
├── internal/
│   ├── api/          # HTTPルーティングとリクエストハンドラー
│   ├── voting/       # ドメイン型とそれに関連するロジック
│   └── datastore/    # DynamoDBの読み書き
├── docs/             # Swagger UIの静的サイト（GitHub Pagesで配信）
├── template.yaml     # AWS SAM/CloudFormationのインフラ定義
└── justfile          # プロジェクト固有のコマンドと設定（Makefileに相当）
```

## ローカル開発

### 前提条件

- **[Go](https://go.dev/doc/install)**：プロジェクトの主な言語。
- **[Python](https://www.python.org/downloads/)**：静的ドキュメントのローカルサーバーを起動するためだけに使用。
- **[Docker](https://docs.docker.com/get-started/get-docker/)**：ローカルのLambda・API GatewayエミュレーターとDynamoDBコンテナに使用。
- **[AWS SAM CLI](https://docs.aws.amazon.com/serverless-application-model/latest/developerguide/install-sam-cli.html)**：SAMインフラのローカルエミュレーションとデプロイに使用。
- **[Just](https://github.com/casey/just#installation)**：開発で使用するコマンドを保存・実行するためのコマンドランナー。

### ローカルでの起動

1. Dockerデーモンを起動した状態で、以下のコマンドを実行します。

```sh
just       # Dockerネットワーク・DynamoDBコンテナ・APIを起動（ポート3000）
just docs  # 別のターミナルで、Swagger UIドキュメントのサーバーを起動（ポート8000）
```

2. ブラウザで [http://localhost:8000](http://localhost:8000) を開いてインタラクティブなドキュメントを確認します。
3. 「Servers」ドロップダウンから `http://localhost:3000` を選択します。
4. 「Try it out」機能を使ってローカルのエンドポイントを叩きます。

利用可能なすべてのレシピ（コマンド）は [`justfile`](justfile) に記載されています。（`just --list` で一覧を確認できます。）

## テスト

```sh
just test     # すべてのテストを実行
just test -v  # すべてのテストを詳細出力付きで実行
```

テストは3つのパッケージ（`api`、`voting`、`datastore`）すべてをカバーし、以下の方針に従っています。

- **依存性逆転と依存性注入**：`api`パッケージと`datastore`パッケージは具体的な実装ではなく、インターフェースに依存しているため、テストでモック実装に差し替えやすくなっています。
- **柔軟なモック**：手書きのモックは`nil`フォールバック付きの関数フィールドを使用していて、インターフェース全体を毎回実装しなくても、各テストケースに必要な振る舞いだけを注入できます。
- **テーブル駆動テスト**：Goのテーブル駆動パターンを使用し、同じロジックに対して複数のテストケースを効率的に実行できるよう整理されています。
- **外部テストパッケージ**：すべてのテストファイルは外部テストパッケージ（例：`package api_test`）を使用していて、内部実装の詳細にアクセスせず、利用者と同じ視点で公開APIをテストしています。

## 優先順位付投票制について

Verdictは、優先順位付投票制（即時決選投票）という投票アルゴリズムを実装しています。このアルゴリズムにはいくつかの種類がありますが、ここで使用しているのは以下の通りです。

### 投票方法

一つだけの選択肢を選ぶのではなく、投票者はすべての選択肢を好みの順に順位付けします。

### 勝者の決定

相対多数しか持たない選択肢を直接選ぶのではなく、アルゴリズムはまずいずれかの選択肢が過半数の票を得ているかを確認します。過半数を得た選択肢がなければ、最も票の少ない選択肢が除外され、その票が投票者の次の順位の選択肢に再配分されます。この除外のプロセスは、ある選択肢が過半数を得るまで繰り返されます。

### 最下位が同票の場合

各ラウンドでは最も票の少ない選択肢が除外されますが、複数の選択肢が最下位で同票だった場合はどうなるでしょうか。この場合、同票の選択肢のみを対象とした決選投票がシミュレートされます。投票者はすべての選択肢に順位を付けているため、任意の選択肢の部分集合内での優先順位をアルゴリズムで判断することができます。再び最下位で同票が生じた場合、この決選投票アルゴリズムは再帰的に続きます。

複数の選択肢が最下位で同票だけでなく、それらへの順位付けも完全に等しいという状況も起こり得ます。選択肢と投票者の数が非常に少ない場合を除けば稀ですが、この場合は最下位の選択肢のうちの一つが擬似乱数生成によって除外されます。
